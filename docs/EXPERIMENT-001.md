# Experiment 001 — Event-Storm Falsification Challenge

## Question
Can a service recover from receiver lag without losing its ability to shut down properly?

## Mechanism
A bounded channel retains 32 messages. Publishing 300 events while the consumer is not reading causes 268 messages to drop. The consumer must observe lag but not interpret lag as a closed channel or explicit shutdown.

## Competing implementations
- **buggy:** `Lagged` incorrectly terminates the service.
- **naive:** ignores `Lagged` but also ignores legitimate termination conditions.
- **correct:** ignores `Lagged`; terminates on `Closed` or explicit sticky shutdown request.

These are prewritten candidates. **They are not generated by AI in this milestone.**

## Falsification experiment
1. Verify a quiet service stays active.
2. Inject a controlled event burst; look for premature termination.
3. Try a naive modification that keeps it alive under a burst.
4. Run independent shutdown/closure experiments. The naive patch should fail.
5. Verify the third candidate satisfies all invariants.
6. Export trace and SHA256 evidence; do not infer correctness beyond tested invariants.

## Evidence standard
A passing result has an observed service state matching each predeclared invariant. No LLM prose can override that state. There is no simulated 'Meta API success' in the baseline; real API selection is separately labeled and requires the developer's own key.

## Limitations
No live network, actual OS concurrency, patch synthesis, or exhaustive formal verification. Deliberately scoped so the first claim is testable.
